# Assumptions

This document lists the assumptions made where the requirements were not explicit.
For each one it gives the **assumption**, the **reason**, and **how it is implemented**.

---

## Borrowers

### 1. Email uniquely identifies a borrower
- **Assumption:** Two borrowers cannot share an email address.
- **Reason:** Without a natural key, the same person could register many times, and borrow limits or history would be meaningless.
- **Implementation:** `BorrowerService` checks `existsByEmail` and returns **409 Conflict**. The DB also has a unique constraint (`uq_borrower_email`) as a backstop.

### 2. Email comparison is case-sensitive as stored
- **Assumption:** Emails are stored exactly as sent and not normalised, so `A@x.com` and `a@x.com` count as different.
- **Reason:** Keeps the implementation simple. Normalising emails (for example, to lowercase) is a policy decision.
- **Future:** Lowercase emails before checking and saving, and use a case-insensitive unique index.

### 3. Borrower ids are generated by the system
- **Assumption:** Clients send only `name` and `email`. The `id` is assigned by the database (identity column).

## Books

### 4. "Book" in the API means a physical copy
- **Assumption:** The `id` returned by `POST /books` and used in `/books/{bookId}/borrow|return` identifies one **physical copy**, not a title.
- **Reason:** The requirement says that registering the same ISBN twice gives different book ids, and that a single book id can only be borrowed by one member at a time.
- **Implementation:** Two tables:
  - `book_title`: ISBN (PK), title, author. One row per ISBN.
  - `book_copy`: id (PK), with a foreign key to `book_title`. One row per physical copy.

### 5. Same ISBN means same title and author
- **Assumption:** Each ISBN maps to exactly one title and author. Registering an existing ISBN with a different title or author is an error.
- **Implementation:** Returns **409 Conflict**. If they match, a new copy is created and **201** is returned.
- **Comparison:** The match is **exact and case-sensitive**. `"Harry Potter"` and `"harry potter"` are treated as different, so the second gets a 409.

### 6. ISBN format
- **Assumption:** The ISBN is sent without dashes or spaces. Both ISBN-10 and ISBN-13 are accepted.
- **Implementation:** Regex `^(?:\d{9}[\dXx]|97[89]\d{10})$`
  - ISBN-10: 9 digits followed by a digit or `X`/`x`
  - ISBN-13: starts with `978` or `979`, then 10 more digits
- **Not done:** The **check digit is not validated**, so a well-formed but invalid ISBN is accepted.
  ISBN-10 and ISBN-13 forms of the same book are treated as **different** ISBNs.

### 7. Availability is derived from borrowing records
- **Assumption:** A copy is available exactly when it has no open borrowing.
- **Implementation:** There is no `available` column. `GET /books` checks for a `borrowing` row with `returned_at IS NULL`.
  Status can never get out of sync with the borrow history.

## Borrowing & Returning

### 8. One active borrower per copy
- **Assumption:** A copy can be borrowed again only after it is returned. This is the core concurrency requirement.
- **Implementation** (two layers):
  1. Inside `@Transactional`, the service checks for an active borrowing and returns **409** if there is one.
  2. A partial unique index `uq_active_borrowing ON borrowing (book_copy_id) WHERE returned_at IS NULL` ensures that two concurrent requests can't both succeed. If one passes the check but loses the race, its `DataIntegrityViolationException` is turned into **409**.

### 9. Only the original borrower can return a copy
- **Assumption:** The `borrowerId` in the return request must match the borrower who borrowed the copy.
- **Reason:** Stops one member from closing another member's borrowing by mistake or on purpose.
- **Implementation:** A mismatch returns **409 Conflict** and the borrowing is left unchanged.
  The returning borrower doesn't need to exist as a separate lookup: the id is only compared with the open borrowing.

### 10. Returning a copy that isn't borrowed is a client error
- **Assumption:** Returning a copy with no open borrowing is an invalid request, not a no-op.
- **Implementation:** Returns **400 Bad Request**. A copy id that doesn't exist returns **404 Not Found**.

### 11. Borrow and return use `POST` with a JSON body
- **Assumption:** Both actions are state-changing commands on a copy, so they use `POST /books/{bookId}/borrow` and `POST /books/{bookId}/return`, with `{ "borrowerId": … }` in the body.
- **Reason:** It's simple for clients, and each borrow creates a new `borrowing` resource, so the call isn't idempotent.

### 12. No borrow limit per borrower
- **Assumption:** A borrower can hold any number of copies at once, including several copies of the same title.
- **Future:** A limit (for example, a maximum of 3 active borrowings) could be added in `BorrowingService.borrowBook`.

### 13. No due dates or fines
- **Assumption:** Borrowing has no time limit. A copy stays borrowed until it is returned.
- **Implementation:** Only `borrowed_at` and `returned_at` are recorded. Adding `due_at` later wouldn't require changing existing data.

### 14. Borrowing history is kept
- **Assumption:** Returning a copy closes the borrowing record (sets `returned_at`) and does not delete it.
- **Reason:** Keeps an audit trail of who borrowed what and when, at no extra cost.

### 15. Timestamps are UTC
- **Assumption:** All timestamps are generated by the server using `Instant.now()`, stored in UTC, and returned in ISO-8601 format, for example `2026-11-02T10:15:30Z`.
  Clients can't set borrow or return times.

## Scope & Non-functional

### 16. No update or delete endpoints
Updating or deleting borrowers, titles, or copies was not requested, so it isn't implemented.
The data model doesn't prevent adding these later. Deleting copies that have history would need soft deletes.

### 17. No authentication or authorization
The API is open, because security was not part of the requirements. In production, it would sit behind an auth layer such as OAuth2 or JWT, with staff and member roles.

### 18. No pagination, filtering, or search
`GET /books` returns every copy. That's fine for an assignment-sized catalogue. In production, it would need pagination and search by ISBN, title, author, or availability.

### 19. Single library, single database
There is one library location and one PostgreSQL instance, with no multi-tenancy or branches.

### 20. API versioning via URL
All endpoints are under `/api/v1`, so breaking changes can be released under `/api/v2` without affecting existing clients.

### 21. Architecture
The code uses a layered architecture (`controller → service → repository → entity`), with DTOs at the API boundary.
Business rules live only in the service layer, which is why it is the focus of the unit tests.
